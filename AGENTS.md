# AGENTS.md — tt-awesome

## What this is

tt-awesome is a curated, machine-readable directory of the Tenstorrent
ecosystem: projects, AI models, kernels, compilers, dev tools, guides, and
research, contributed by the community and the Tenstorrent team. Planet
Tenstorrent (`/planet/`) aggregates community articles, talks, and release
announcements alongside it.

**Intent:** developers and agents building on Tenstorrent hardware need prior
art, tools, articles, and the latest releases. tt-awesome and Planet
Tenstorrent provide them in a form you can rely on. Check here before building
something new.

## Machine-readable surfaces

| Surface | URL | Use it for |
|---|---|---|
| Entry database | `data.json` | The richest source: every entry with structured links, releases, packages, tags, and hardware fields. |
| Entry pages | `entry/<id>/` | One readable HTML document per entry; content lives in `#entry-content`. Enumerated in `sitemap.xml`. |
| Sitemap | `sitemap.xml` | Discover every entry page URL. |
| LLM index | `llms.txt` | Compact categorized index sized for LLM context windows. |
| JSON Feed | `feeds/feed.json` | Combined releases, new entries, and articles (JSON Feed 1.1). |
| Atom feeds | `feeds/releases.xml`, `feeds/new-entries.xml`, `feeds/articles.xml` | Latest stable releases, newly added projects, and articles/papers/talks. |

All paths are relative to the site root
(`https://docs.tenstorrent.com/tt-awesome/`).

## Freshness

GitHub metadata (stars, releases, changelogs) refreshes nightly via CI, so
release and version information here is current. Feed items carry publish
timestamps.

## Working in this repository

The rest of this file is for people and agents changing the repo itself.
`CONTRIBUTING.md` has the entry schema, package table, affiliation policy,
and category slugs. `.github/CI.md` has the scheduled workflows, the
summarization backend, and how to debug a failed nightly run.

### Layout

| Path | Role |
|---|---|
| `entries/<category>/*.json` | Source of truth. One file per entry. `scripts/validate.py` enforces the schema. |
| `src/_data/github_meta.json` | Stars, releases, changelogs per repo. Written nightly by `scripts/fetch_github_meta.py`. |
| `src/_data/planet_feeds.json` | Every Planet item: release summaries from `scripts/summarize_releases.py`, plus YouTube, arXiv, Reddit, blogs and connpass from `scripts/fetch_planet_feeds.py`. One record per item, keyed by URL, sorted newest first by `dateISO`. |
| `src/_data/planet_declined.json` | URLs reviewed and rejected, so no fetcher proposes them again. Add to it with `scripts/decline_planet_item.py`. |
| `scripts/llm_client.py`, `prompts/*.prompt.yml` | The LLM front door and its prompts. The backend is chosen by the `SUMMARY_PROVIDER` repository variable. |
| `.eleventy.js` | All rendering logic, written as filters so tests can call them. `planetItems` builds the Planet page; `buildFeedContentHtml` builds every feed's rich content. |
| `README.md` | Generated from `entries/` by `scripts/generate_readme.py`. Tracked. Regenerate it after changing entries. |
| `data.json` | Generated by `scripts/generate_data_json.py`. Gitignored; CI generates it before every build. |

### Commands

```
python3 scripts/validate.py         # entry schema
python3 -m pytest tests/ -q         # python suites
npm run generate                    # README.md + data.json
npm run build                       # Eleventy; run before the JS suites
node tests/test_entry_pages.js      # build-output assertions, including data.json present and fresh
node tests/test_data_files.js
node tests/test_eleventy_filters.js
node tests/test_recent_releases.js
```

There is no test runner configuration. `build-check.yml` runs the JS suites on
every pull request that touches `src/`, `entries/` or `tests/`. The JS filter
tests call `.eleventy.js` with a stub config that captures `addFilter`, which
is why helpers meant to be tested are registered as filters even when no
template uses them.

### Entries

* The `id` is the filename and the permalink. Never change it. If a project is
  renamed or moves, update `name`, `url`, `description` and `links` and keep
  the id. To retire an id, list it in `previous_ids` on the successor so a
  redirect stub is generated.
* `affiliation` is `official` for repos in a Tenstorrent-owned org (the
  validator enforces this from the repo URL), `affiliated` for Tenstorrent
  staff publishing on personal accounts, and `community` otherwise. A commit
  email or document ownership is better evidence of staff status than a
  directory lookup; the directory misses people.
* Check the repo before writing. Take hardware support from the README or
  support matrix, the language from the source directories (GitHub's byte
  count is skewed by vendored code), and the license from the LICENSE file.
  Verify that a package exists on PyPI, the PPA or the Hub before adding a
  `packages` entry; a wrong name renders an install command that fails.
* A `tt-model` package renders `tt serve <ns>/<bundle>`. Only add one for a
  Hugging Face repo that carries the `tt-model-catalog` tag; that tag is the
  author's explicit publish step. Check it with
  `curl -s https://huggingface.co/api/models/<ns>/<name>`.
* Recency matters. Check `pushed_at` (or the last commit on the branch that
  holds the Tenstorrent work, for forks) and leave out projects that have gone
  quiet.
* `added_at` is the date the entry was first listed. It drives the new-entries
  feed. Use today's date for a new entry.
* Set `hidden: true` to keep an entry out of the README and site. Set
  `featured: true` to show the star and sort it to the top of its tier.

### Links and the Planet page

* Link types `article`, `lesson`, `paper`, `talk`, `video` and `demo` make the
  entry produce a Planet card dated `added_at`. `repo` and `website` do not.
  Use `website` for docs sections and companion repos that should appear on the
  entry card only.
* One entry makes one Planet card, whatever the number of article links. When
  every article link on an entry already has a published Planet item, the
  entry produces no card and the items render with their own dates and
  headlines.
* Planet items for a single post or video can be written by hand. Use the
  exact shape the fetchers emit, set `approved: true`, and insert the record
  in `dateISO` order. Items without `approved: true` never render.
* Do not add a feed subscription to `fetch_planet_feeds.py` unless every item
  the feed publishes is about Tenstorrent. The fetcher does no topic filtering.
* Medium blocks direct fetches; `https://medium.com/feed/@<handle>` returns the
  full post body in `content:encoded`.

### Releases

* `summarize_releases.py` publishes one item per release that is in
  `github_meta.json` and absent from `planet_feeds.json`. It has no date
  window: adding an entry with old releases publishes all of them at their
  real dates. The Planet page groups releases of one project that fall within
  a chained three-day window into one card.
* Release bodies shorter than `SPARSE_LIMIT` characters are skipped, unless
  they point at a changelog file or a compare link, which the script follows.
* The LLM API key exists only in CI. To add a release item locally, write it
  by hand to the same schema and follow `prompts/summarize-release.prompt.yml`.

### Generated and bot-owned files

* The nightly workflows own `github_meta.json` and `planet_feeds.json` and open
  pull requests with the changes. To add one repo by hand, import the
  functions from `scripts/fetch_github_meta.py` and write only that record.
  Running `main()` rewrites every record and buries the change in star churn.
* Regenerate `README.md` and commit it with any entry change. Do not commit
  `data.json`.

## Contributing

Each entry is a single JSON file under `entries/<category>/` in the
[tt-awesome repository](https://github.com/tenstorrent/tt-awesome). To add or
correct an entry, open a pull request there. See `CONTRIBUTING.md`.
